## 3. P0 · 高优先级（建议本轮修）

### 3.1 异步链路里跑同步检索，阻塞整个事件循环

- **位置**：`backend/core/rag_engine.py:15-17` → `backend/rag/vector_store.py:42`
- **证据**（已读源码核实）：

```python
# rag_engine.py —— 声明为 async
async def retrieve(self, query, ...):
    ... self.store.search(query, ...)   # ← 同步调用

# vector_store.py:42 —— 普通 def
def search(self, query: str, top_k: int = 5, doc_type=None): ...
```

- **问题**：`search` 内部是 `embedding_model.embed_query()` + `collection.query()`，两处都是同步阻塞调用（可能走 HTTP 或本地 BGE 推理）。在 FastAPI 的 async 路由里直接 await 不到、又跑在主线程上，**一个检索就能卡住所有并发请求**。
- **影响**：高并发弹幕场景下吞吐量显著下降，WebSocket 广播延迟抖动。
- **建议**：`await asyncio.to_thread(self.store.search, ...)`（改动最小），或把 embedding/检索整体下沉到线程池。

### 3.2 采集回调三步操作无异常隔离，单条弹幕失败会中断整条采集任务

- **位置**：`backend/routers/douyin.py:155-183`（`_handle_captured_danmaku`）、`douyin.py:198-199`（调用点）
- **证据**（已核实）：

```python
# douyin.py:198  —— 调用点无 try/except
async def on_danmaku(user: str, content: str):
    await _handle_captured_danmaku(session_id, anchor_id, user, content)

# _handle_captured_danmaku 内部三步均无异常保护：
#   1) AsyncSessionLocal + db.commit()   ← DB 异常
#   2) livestream_agent.process_danmaku() ← LLM 异常（超时/额度/网络）
#   3) await manager.broadcast({...})     ← 广播异常
```

- **问题**：三步各自都可能抛异常，且异常会沿 `on_danmaku` → 采集循环向上冒泡。LLM 是最不稳的一环——一旦 402/超时，采集循环直接被打断。
- **影响**：**单条弹幕失败 = 采集停摆**，前端表现为"刚开始采集就断了"，且无日志可查。
- **建议**：三步各自 `try/except + logger.warning`；DB 失败跳过本条、LLM 失败降级为"仅落库不分析"、广播失败忽略（`broadcast` 内部已有 per-connection try，但它守在发送环节，不覆盖前面的异常）。

### 3.3 向量库文档 ID 用列表长度生成，重复入库会导致 ID 复用

- **位置**：`backend/rag/vector_store.py:30`
- **证据**：`doc_id = f"{doc.get('doc_type', 'doc')}_{len(ids)}"` —— 每次调用从 0 开始计数。
- **问题**：第二次 `add_documents` 时 `len(ids)` 又回到 0，生成 `doc_0`、`doc_1`… 与首次入库的 ID 完全重合。ChromaDB 对同 ID 是 **upsert 语义**，会**静默覆盖旧文档**。
- **影响**：知识库增量重建时，旧分片被悄悄替换，检索结果不可预测 —— 这类问题极难排查（表现为"召回率莫名下降"）。
- **建议**：ID 里带上 `doc_type + 内容 hash`（如 `f"{doc_type}_{hashlib.md5(content.encode()).hexdigest()[:12]}"`），或使用 `uuid4()`。

### 3.4 WebSocket 断线后连接方清理与重连判定存在缺口

- **位置**：`frontend/src/utils/websocket.ts:61-66`、`frontend/src/stores/index.ts:26-38`
- **证据**：

```ts
// websocket.ts —— disconnect() 只 close，不移除监听器
disconnect() { this.ws?.close() }   // onopen/onmessage/onclose/onerror 仍挂在旧实例上

// stores/index.ts:26 —— 幂等判定
if (wsClient && sessionId.value === sessionIdStr) return   // sessionId 没变就直接 return
```

- **问题**：
  - 监听器不摘 → 旧实例被闭包持有，**内存泄漏**；
  - `sessionId` 未变但连接已断（服务器重启、网络闪断）时，`connect()` 会**误判为"已连接"而直接返回**，导致长时间收不到推送。
  - 注：`websocket.ts` 里已有 `closedByUser` 标记的重连兜底，能覆盖"非主动关闭"场景，但**主动 disconnect 后同 sessionId 重连仍走不回来**。
- **建议**：`disconnect()` 内显式置空 `onopen/onmessage/onclose/onerror`；`connect()` 的幂等判定加一条 `&& wsClient.isOpen()`。

### 3.5 直播间页面卸载未断开 WebSocket，连接资源未释放

- **位置**：`frontend/src/views/LiveRoom.vue:324-326`
- **问题**：`onUnmounted` 只 `clearInterval(cooldownTimer)`，没有断开 WebSocket。用户切页后连接仍然保留，后端 `ConnectionManager.sessions` 中仍持有该连接，弹幕会继续向该连接推送但已无接收方。
- **影响**：内存/连接双泄漏；多切几次页面后后端广播耗时线性上升。
- **建议**：`onUnmounted` 中补 `wsStore.disconnect()` 或 `websocket.disconnect()`。

### 3.6 图表页 resize 监听器不摘，组件复挂即泄漏

- **位置**：`frontend/src/components/StatsChart.vue:76-83`
- **证据**：`onMounted` 里 `window.addEventListener('resize', () => chart?.resize())` 用的是**匿名箭头函数**，`onUnmounted` 只做了 `chart?.dispose()`，无法 `removeEventListener`。
- **影响**：看板来回切换页面，resize 回调累积，配合已 dispose 的 chart 实例 = 持续的无效调用 + 泄漏。
- **建议**：把 handler 提到具名变量，`onUnmounted` 中 `removeEventListener` 后再 `dispose`。

### 关于 `backend/sql/` 两个文件（单独说明）

OCR 报了 5 条 SQL 相关 high（COMMENT 语法、行内 `INDEX`、外键），其中**两条是真的**：
- `01_schema.sql` 大量使用 MySQL 的 `COMMENT '…'` 子句 → **SQLite 会直接报语法错**；
- `01_schema.sql:31-32,64` 把 `INDEX` 写在 `CREATE TABLE` 内部 → **SQLite 不支持行内索引**。

但关键在于：**这两个 .sql 文件在整个仓库里没有任何一处被引用**（已全仓 grep `\.sql` / `01_schema` / `02_seed`，Python 侧零命中）。实际建表走的是 SQLAlchemy `create_all` + `models/database.py` 里的 `_migrate_*` 增量迁移。

**结论**：这是一对**用 MySQL 语法编写、当前未被接入运行的文件**。建议二选一 —— 要么改写为合法 SQLite 语法并真正接入初始化流程；要么在文件头加注释标注"仅作 schema 参考文档，不参与运行"，避免后人误执行。**优先级：低，但值得标注。**
